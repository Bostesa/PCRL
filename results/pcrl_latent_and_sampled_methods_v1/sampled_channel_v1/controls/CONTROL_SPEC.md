# R13 sampled-channel controls

**Status:** prefit control contract for R11/R12/R00 integration. No Adult fit is admitted by this file. The effective campaign seal must bind source, bank, action map, gate, objective, optimization ceiling, seeds and actual complete view before a control runs.

## Common service and fit rules

The provider computes the two frozen U0 score vectors and admitted fine cells from the 83 permitted predictors. Central controls may use both score vectors, both fine cells and the same fixed entropy/margin summaries as the joint candidate. Local controls use only their own recipient's score and cell. Every fitted arm uses R11's **same globally canonical public bank**, same-class action lists, at most four public choices per recipient and at most sixteen public output pairs per person. R01's current fixed-bank audit reports 16 income and 321 occupation public IDs and 64/641 input fine cells in both seeds; independent source parity is still pending. Occupation class 5 has only one bank ID, so its action row has one choice. Implementations must support 1–4 actions and fixed padded gate-slot semantics. An output ID always names one public probability/decision vector, independent of the input fine cell or local action position. Each released probability is the fixed public vector named by the sampled ID. The input fine cells, action indices, gate probabilities and unsampled mean are not released.

The candidate and every central control share the two-score provider input scope, bank, class restriction, action geometry, utility caps, public output capacity, training people, model seeds, three predeclared release realizations, full view, attack slate and total per-arm compute ceiling. A control may have fewer free gate parameters because of a structural independence restriction; report the exact count and do not call equal output capacity equal model capacity. Freeze checkpoint and start-selection rules before screening. The task-only workers receive only admitted scores, fine cells, task labels and reference losses; their data object and loader have **no SEX array**. Protected controls may use SEX only during admitted fitting. No new fit uses INNER labels or old assessment arrays.

`A-TASK-DET` and `A-DET-PRIVATE` use a separate 12→16→16 tanh gate with **hard argmax forward** and softmax-gradient backward. They do not round any stochastic fit. Two independent identity-biased and uniform starts run the same sealed update count and matched total CPU ceiling as the stochastic arm. Exact hard public-code losses and recovery are replayed at update 0, each sealed replay interval and the final update. Among complete starts, each start's best exactly feasible replayed checkpoint by primary objective and predeclared ties seeds one fixed deployable bias pass: slots 0–15, deltas `[-0.5,-0.1,+0.1,+0.5]` in that order, at most 64 attempted trials per start. A trial is accepted only if all four loss caps (and private local guards) pass **literally at or below** their limits and it improves primary objective by more than `1e-10`, or ties within `1e-10` and improves active public pair/code count, then summed task loss. If no feasible checkpoint exists, the terminal checkpoint seeds that polish as a repair attempt. No per-person reassignment is permitted. All updates, replays and 64 trials per start must finish inside the same per-arm ceiling; a cutoff makes the deterministic arm incomplete for stochastic attribution. The final eligible checkpoint is chosen by exact primary/ties only after both starts finish. These are bounded heuristics, not exact optima.

`controls/deterministic_trainer.py` binds R12's padded `PreparedLaw` to the exact per-row canonical identity pair, but the caller must independently compare FIT row-order and action-map hashes to the sealed R01/R11 manifests before calling it. `controls/deterministic_policy.py` deploys the fitted hard gate as a one-hot public law through R12's cached release adapter. R12's mechanism hash includes the policy law kind, so hard and stochastic gates with identical weights cannot share a cache identity. Endpoint replay must use this deployed hard policy, never R12's default softmax policy with the same weights.

Central PRODUCT uses two 12→16 tanh→4 factors, 276 parameters each and 552 total. Both read both provider score vectors and their four summaries. LOCAL factors instead receive only their own score/fine cell and own summaries through separate fitting capabilities: widths 4 and 8, with 148 and 212 parameters. A paired release may coordinate caching without giving one local factor the other's input. SEQ stage 1 is a 276-parameter central factor. Stage 2 reads both scores plus a learned 16-vector embedding of the **actual first global public code** added to its hidden preactivation, with `276+16*Z_first` parameters. Thus SEQ12 has 808 and SEQ21 has 5688 total parameters for canonical bank sizes 16/321. These capacity differences and a matched total CPU ceiling must be reported; a short ceiling may undertrain the larger sequential control and limit joint-design attribution.

The prefit equal-update allocation is PRODUCT: two independent starts × 300 full-FIT updates, jointly updating both factors. LOCAL: each own-purpose factor gets two starts × 150 updates and is selected on its own exact task/local recovery before pair composition. SEQ in each order: stage 1 gets two starts × 150 updates, is selected and frozen before the FIT first draw, then stage 2 gets two starts × 150 updates on that cached first draw; only exact full final-law caps/guards select stage-2 checkpoints. The whole PRODUCT, LOCAL or SEQ arm shares one total CPU ceiling with JOINT-STOCH. Equal update counts do not imply equal optimization difficulty, especially for SEQ21's larger embedding. All starts, updates, checkpoint replays and custody work count against the ceiling; truncation makes the affected attribution incomplete.

Every stage-2 embedding row is initialized deterministically from the *public first bank*: `E0[z,j]=bank_first.probability[z,j mod K_first]` for `j=0..15`, float64 in canonical code order. There is no embedding weight decay. A code absent from the one frozen FIT first-draw keeps its row exactly at E0; deployment and exact full-law replay still support it. Count seen/unseen first codes and the full frozen-first-law FIT probability mass on unseen codes; report INNER unseen mass after configuration freeze only. An appreciable unseen mass limits the sequential comparison. Stage 2 has no hidden input fine token beyond both admitted scores and the actual emitted first public code. R12's cached release sampler runs first-stage draw, passes that code into the conditional second factor, and stores the one pair under the fixed query contract.

Expected NLL/Brier are sums over the probabilities of actual public outputs, with observed task labels and the exact fixed bank rows. They are not losses of an averaged output vector. Each cap is the more restrictive of the inherited U0 and Ucal fitting-role references plus 0.010 NLL or 0.005 summed multiclass Brier, with both reference excesses reported separately on INNER. An identity action is a utility witness only if it actually meets these caps on the comparable rows. No pointwise guard or post-channel calibration is introduced.

## Exact sequential sampling aliases

For each fitted input, a central joint law satisfies both factorizations `q(z1,z2|x)=q(z1|x)q(z2|z1,x)=q(z2|x)q(z1|z2,x)`. `joint_law_compiler.py` compiles **both** orders from sparse `(global_id1, global_id2, mass)` triples. It first aggregates duplicate public pairs. When a first-stage output has zero marginal mass, its conditional is one-hot on the lowest admissible second public ID; this has no effect on the emitted joint law. Rational tiny cases replay exactly. Numeric fitted rows require a recorded maximum probability-sum residual and maximum pair-law replay residual. R12's runner must call `verify_admitted_rows` on **every** FIT input row, supplying ordered FIT IDs, source predicted classes and fixed bank decisions. It checks order/count against those supplied IDs, class-restricted allowed IDs and both factorization residuals, and emits only hashes and aggregates. **Before that call**, the runner must compare the supplied FIT row-order hash to R01's sealed role manifest, compare the action-map hash to R11's sealed bank/action package, and check each supplied allowed-ID tuple equals the frozen map at that person's fine cell. The wrapper alone cannot establish those source identities. Missing comparisons mean there is no full alias proof. The receipt is an engineering equality check, not a separately learned baseline. These aliases cannot support a joint-sampling novelty claim.

## Release, attack and completion gate

The service returns one cached sampled public code/probability/decision per person and recipient under its model version. It uses provider-private randomness, coherent duplicate-group and aligned-person handling, and no redraw endpoint. The three fixed complete realizations are separate development release draws, not extra populations. Complete fresh attacks read code IDs, probabilities, decisions and all transmitted metadata for each recipient and pair; an attacker may ignore either recipient. Fit/tune readers only on admitted attack-fitting groups, freeze them before INNER, and carry release variance into the paired uncertainty plan.

Every arm ends completed, exact alias, technically failed, missing source, budget cut or not triggered under the sealed rule. A stochastic win must clear its own deterministic and central-product alternatives; a joint-design win must additionally clear local and both freeze-first design orders. Equal or near-equal reported AUC is not an alias without exact output-law/release equivalence. A method result is exploratory on reused Adult development roles.
